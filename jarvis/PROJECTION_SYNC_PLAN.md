# JARVIS Projection-Sync Plan

**Date:** 2026-06-15
**Scope:** Close the operational drift between the canonical `dev_graph/` markdown and the four
downstream projections the JARVIS stack consumes. **Glue, not architecture** — ADR-010's model
(markdown canonical, projections rebuildable, never hand-edited) is sound; this plan only makes the
rebuild one atomic action so the projections stop diverging.

**Status: IMPLEMENTED (2026-06-15).** Rec 1 — `export_graph_json.py` writes both `graph.json` copies
in one run (`--out` for a single path; `--stdout` is now pure JSON, diagnostics → stderr). Rec 2 —
`jarvis/resync-devgraph.ps1` (dry-run validate → `--clear` → export both; fail-fast on the
`--- Summary ---` marker, since the sync exits 1 on the 5 normal skipped edges). Rec 3 —
`jarvis/hooks/pre-commit` (+ `install.sh`) blocks a `dev_graph/**.md` commit that leaves either
`graph.json` stale; DB-free. Rec 4 — `graphStats()` in `hud/src/data/graph.ts` drives the OPS
architecture line + GRAPH-3D tab title from the loaded projection; the stale `~140 nodes ·
ADR-001–009` strings are fixed. Curated narrative panels (SERIES/ORBITS, 12 Pivotal Points) stay
static by design. The text below is the original design rationale.

---

## Problem statement

The dev_graph markdown (163 `.md`, 159 content nodes) is the single source of truth. It fans out into
**four downstream projections, every one regenerated by hand**:

| # | Projection | Built by | Trigger today |
|---|---|---|---|
| 1 | Neo4j graph store | `sync_to_neo4j.py --clear` | manual |
| 2 | `jarvis/frontend/graph.json` | `export_graph_json.py` | manual |
| 3 | `jarvis/hud/public/graph.json` | `export_graph_json.py --out …` (a *separate* invocation) | manual |
| 4 | `jarvis/hud/dist/graph.json` | `npm run build` bakes `public/` | manual |

There is **no automation**: `.git/hooks` is empty, no husky / pre-commit / CI, and neither `start.ps1`
nor the build regenerates anything. `dev_graph/CLAUDE.md` writeback step 10 ("re-sync Neo4j") is the
only instruction and it doesn't mention the two `graph.json` copies or the rebuild.

**Why this matters:** one logical action ("the dev_graph changed") requires 3–4 manual steps against
3–4 targets, so they silently diverge. And the HUD leans on `graph.json` more than on Neo4j — in
`hud/src/hooks/useGraph.ts`, `buildIndex(graph)` is built from `graph.json` *even in live mode*, and
the backend `/ask` seed matcher (`backend/app.py` `_graph_doc`) reads `graph.json` too. So a stale
`graph.json` degrades answering **even against a freshly synced Neo4j**.

### Drift already present (evidence)

- `hud/src/components/ops/Architecture.tsx` hardcodes *"dev_graph: ~140 nodes · ~920 edges ·
  ADR-001–009"* — the real graph is **159 nodes / 1113 edges / ADR-010 exists**.
- Three architecture nodes (`Context Map.md`, `Infrastructure Diagram.md` ×2) are modified in the
  working tree and **newer than the committed `graph.json`** (last generated 2026-06-14).

---

## Recommendation 1 — Kill the duplicate `graph.json`

**Today:** `export_graph_json.py` writes only `frontend/graph.json`; `hud/public/graph.json` is a
hand-copied dupe kept in sync by a *separate* `--out` invocation. This is the most fragile link —
nothing guarantees the two are byte-identical.

**Do:** make the exporter write **both paths in a single run** (default behavior), so one invocation
can never leave the two copies out of step.

- Add a `--targets` / multi-out default to `export_graph_json.py`: write
  `frontend/graph.json` **and** `hud/public/graph.json` from one parse.
- Keep `--out` for ad-hoc single-target use, but the no-arg run writes both.
- Alternative (heavier, deferred): collapse to one physical file and point both the standalone
  explorer (`frontend/index.html`) and the HUD at it. Not now — two consumers, two conventions; the
  single-run-writes-both approach removes the drift risk without a path refactor.

**Acceptance:** `python jarvis/export_graph_json.py` (no args) leaves
`frontend/graph.json` and `hud/public/graph.json` identical; `diff` is clean.

---

## Recommendation 2 — One `resync-devgraph.ps1`

**Today:** re-projection is `sync_to_neo4j.py --clear` **then** `export_graph_json.py` (×2 paths) —
three steps that can half-run, leaving Neo4j and `graph.json` on different versions of the markdown.

**Do:** add `jarvis/resync-devgraph.ps1` that runs, in order and fail-fast:

1. `python sync_to_neo4j.py --dry-run` (validate the parse offline first)
2. `python sync_to_neo4j.py --clear` (re-project Neo4j)
3. `python jarvis/export_graph_json.py` (re-project **both** `graph.json` — after Rec 1)
4. print the resulting node/edge counts so a stale build is obvious

It must be idempotent and abort on any non-zero step (`$ErrorActionPreference = "Stop"`). This becomes
the **single command** for "the dev_graph changed."

**Then:** replace `dev_graph/CLAUDE.md` writeback **step 10** (currently Neo4j-only) with a call to
this one script, so the canonical writeback moment rebuilds *all* projections together.

**Acceptance:** running `resync-devgraph.ps1` from a clean working tree leaves Neo4j, both
`graph.json` copies, and (after `npm run build`) `dist/graph.json` all on the same node/edge counts.

---

## Recommendation 3 — Optional git `pre-commit` hook (right granularity)

**Granularity:** "on committed dev_graph change," **not** a real-time filesystem watcher. `--clear`
re-projection rebuilds ~1100 edges — heavy and idempotent; the canonical rebuild moment is the
writeback/commit, not every keystroke.

**Do:** a `pre-commit` hook scoped to staged `dev_graph/**.md`:

- **Minimum (recommended first):** *fail the commit* if `graph.json` is stale relative to the staged
  markdown — i.e. run `export_graph_json.py --stdout` and compare to the committed
  `frontend/graph.json`; if they differ, block with "run `resync-devgraph.ps1` before committing."
  This is safe (read-only, no DB needed — the exporter reads markdown like `--dry-run`).
- **Stretch:** regenerate `graph.json` in the hook and `git add` it. Deferred — auto-staging generated
  files in a hook is convenient but can surprise; start with the failing check.
- **Note:** the hook should **not** touch Neo4j (a hook must not require a running DB). Neo4j re-sync
  stays in `resync-devgraph.ps1`; the hook only guards the server-less `graph.json`.

**Acceptance:** committing a `dev_graph/**.md` edit without regenerating `graph.json` fails with a
clear message; committing after `resync-devgraph.ps1` passes.

---

## Recommendation 4 — Decide the dashboard chrome's contract

The HUD has **two component classes** (this is by design, but the boundary should be explicit):

- **Graph-driven** — `data/graph.ts`, `useGraph`, `router.ts`, `GraphView`, `KnowledgeGraph`. These
  read `graph.json` / the live bridge and already follow the dev_graph accurately. No change.
- **Hand-authored presentation constants** — `data/snapshot.ts` (SNAPSHOT/SERIES/ORBITS/VITALS),
  `ops/Architecture.tsx`, `ops/The12PivotalPoints.tsx`, the epoch/roadmap panels. Ported verbatim
  from the source HTML monolith, honestly tagged `SNAPSHOT-DRIVEN`, pinned to the 2026-03-15 snapshot.

**Decision:** keep the curated narrative panels static (they are intentional editorial content, not a
graph view), but stop the **graph-derivable** numbers inside them from drifting:

- **Minimum (do now):** fix the stale string in `Architecture.tsx` (`~140 nodes · ~920 edges ·
  ADR-001–009` → current `159 / 1113 / ADR-001–010`).
- **Better (small):** have the few genuinely graph-derived bits read from `graph.json` at runtime:
  node/edge counts (already in `graph.json.meta`), the ADR range (max `ADR-NNN` id), and the
  `VITALS_GAUGES` module list. Then those numbers can never go stale again.
- **Leave static:** SERIES/ORBITS/SNAPSHOT (market data — a separate refresh pass, see HUD README) and
  the 12 Pivotal Points / epoch narrative (editorial).

**Acceptance:** no hardcoded dev_graph size/ADR-range string remains; `graph.json.meta` drives the
displayed counts, or the one remaining string matches the current projection.

## Sequence

```
Rec 1  exporter writes both graph.json paths in one run    ── unblocks Rec 2 & 3
  │
Rec 2  resync-devgraph.ps1 (sync --clear + export)         ── replaces writeback step 10
  │
Rec 3  pre-commit hook: fail if graph.json stale           ── guards the server-less projection
  │
Rec 4  fix Architecture.tsx string; meta-driven counts     ── independent, do anytime
```

Recs 1–3 are the high-leverage, low-risk slice (no component rewrites, no schema change). Rec 4's
minimum (the stale string) is a one-line fix; its "better" form is a small, optional follow-up.

## Non-goals

- **No real-time watcher / auto-migrate on every save** — wrong granularity for a heavy `--clear`
  re-projection; the commit/writeback moment is the right trigger.
- **No rewrite of the curated panels into graph views** — they are deliberate narrative.
- **No new source of truth** — `graph.json` and Neo4j remain rebuildable projections of the markdown,
  never hand-edited (ADR-010 §4).
